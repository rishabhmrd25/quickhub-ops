# QuickHub Ops — Project Plan

A real-time operations dashboard for a quick-commerce **dark store** (a delivery-only mini warehouse).
All data is fake and generated by a local mock server. This is a learning project.

## 1. Goal

Staff in a dark store need one screen to watch orders arrive, assign a picker and a rider,
move each order through its stages, and keep an eye on stock.

| Role | Can do |
|---|---|
| **Manager** | Everything: see all orders, change status, assign staff, create orders, adjust stock |
| **Picker** | See only orders assigned to them, move them `picking → packed` |
| **Viewer** | Read-only access to orders and inventory |

## 2. Architecture

```
quickhub-ops/               npm workspaces monorepo
├─ packages/shared/         Types, order state machine, permission rules (used by BOTH sides)
├─ apps/server/             Express REST API + WebSocket server, in-memory data, live simulator
└─ apps/web/                React + TypeScript + Vite single-page app
```

**Why a shared package?** The server and the browser must agree on what an `Order` is,
which status changes are legal, and what each role may do. One source of truth means they can't drift.

### Tech choices (and the one-line reason for each)

| Tool | Used for | Why this one |
|---|---|---|
| Vite + React 18 + TypeScript (strict) | Web app | Fast dev server, strong typing |
| **TanStack Query** | Server state (orders, inventory) | Caching, retries, infinite scroll, cache patching for live updates |
| **Zustand** | Client state (session, filters, connection status, toasts) | Tiny, no boilerplate; server data does NOT live here |
| **TanStack Virtual** | Orders table | Renders only visible rows, so 10,000 rows stay smooth |
| React Router (lazy routes) | Pages | Code-splitting: each page is its own bundle chunk |
| React Hook Form + Zod | Multi-step form | Per-step validation, same Zod schema reused on the server |
| Express + `ws` | Mock backend | Smallest thing that gives real REST + real WebSockets |
| Vitest | Unit tests | Same config as Vite |
| Playwright | End-to-end tests | Drives a real browser through the real app |

**Rule of thumb in this codebase:** data that comes from the server lives in TanStack Query.
Data that only the browser cares about lives in Zustand.

## 3. Data model

```ts
Order { id, customerName, address, items[], total, status, pickerId, riderId,
        createdAt, updatedAt, promisedBy, version }
InventoryItem { sku, name, category, stock, reorderLevel, price, version }
User { id, name, email, role }
```

### Order state machine

```
new → picking → packed → out_for_delivery → delivered
 └──────┴─────────┴──→ cancelled        (cannot cancel once out for delivery)
```

Rules enforced on the server (the UI only hides buttons; the server is the real gate):

- `new → picking` needs a picker assigned.
- `packed → out_for_delivery` needs a rider assigned.
- `delivered` and `cancelled` are final.
- Cancelling returns the items to stock.

## 4. API

| Method | Path | Who | Notes |
|---|---|---|---|
| POST | `/api/auth/login` | anyone | Returns a signed token |
| GET | `/api/me` | signed in | Validates a stored token on page reload |
| GET | `/api/orders` | signed in | `status`, `q`, `cursor`, `limit`. Cursor pagination. Pickers only get their own |
| GET | `/api/orders/:id` | signed in | 404 for a picker asking about someone else's order |
| PATCH | `/api/orders/:id/status` | manager, picker (limited) | Body carries `version` |
| PATCH | `/api/orders/:id/assign` | manager | Body carries `version` |
| POST | `/api/orders` | manager | `Idempotency-Key` header |
| GET | `/api/inventory` | signed in | `q`, `lowOnly` |
| PATCH | `/api/inventory/:sku` | manager | `delta` + `version` |
| GET | `/api/staff` | signed in | Pickers and riders |
| GET | `/api/stats` | signed in | Counts per status |
| WS | `/ws` | signed in | Token is sent as the first message (not in the URL, which would end up in logs). Events: `order.created`, `order.updated`, `order.removed`, `inventory.updated`, each with a per-connection `seq` number |

## 5. Edge cases and how each is handled

### Real-time (WebSocket)
| Case | Handling |
|---|---|
| Connection drops | Auto-reconnect with exponential backoff + jitter (1s → 30s cap). Banner shows "Reconnecting…" |
| Events missed while offline | Every event has a `seq`. On reconnect, or if a gap in `seq` is seen, all queries are refetched |
| Burst of 100s of events | Events are buffered and applied in one batch every 250 ms, so React renders once, not 100 times |
| Old event arrives after a newer one | Each order has a `version`; an event with a lower version than the cache is ignored |
| Order changes so it no longer matches the active filter | It is removed from the visible list |
| Rows are added/removed above what the user is reading | Scroll anchoring: the first visible row is remembered and the scroll position is shifted so it stays put. A "↑ N new above" pill offers a jump to the top |
| An order starts matching the active filter | Inserted at its sorted position, but only if that position is inside the pages already loaded |
| Picker's order is reassigned to someone else | Server sends `order.removed` to that picker; it disappears from their list |
| Token expires while connected | Server closes with code 4401 → client logs out, no reconnect loop |
| Tab hidden for a long time | On becoming visible again, data is refetched |
| Server dies silently | Server pings every 15 s; client treats 35 s of silence as dead and reconnects |

### Concurrency
| Case | Handling |
|---|---|
| Two managers edit the same order | Optimistic concurrency: request sends `version`; mismatch → **409**; UI shows "Order changed, refreshed" and reloads it |
| User double-clicks "Create order" | Button disables while pending **and** an `Idempotency-Key` makes the server return the first result |
| Stock runs out between form step 2 and submit | Server re-checks stock, returns **422** with the short SKUs; form jumps back to the items step and marks them |
| Stock adjust would go below zero | Rejected with 422 |

### UI updates
| Case | Handling |
|---|---|
| Status change feels slow | Optimistic update: UI changes immediately, rolls back if the server refuses |
| Illegal transition | Buttons for illegal moves are not rendered; server also rejects with 422 |
| Search typing fires many requests | 300 ms debounce; TanStack Query cancels stale requests |
| Filters lost on refresh | Status and search live in the URL (`?status=picking&q=asha`), so views can be bookmarked and shared |
| Empty / loading / error states | Each page has all three, with a retry button on errors |
| A component crashes | Error boundary shows a fallback and reports the error |

### Auth and roles
| Case | Handling |
|---|---|
| Not signed in | Redirect to `/login`, then back to the page they wanted |
| Signed in but wrong role (e.g. viewer opens `/orders/new`) | "No access" page; nav link is hidden too |
| Token invalid/expired on any request | 401 → session cleared → login page |
| Role checks only in the UI | Never. Every server route checks the permission again |
| Picker guesses another order's URL | Server returns 404 (does not reveal that it exists) |
| Page reload | Session is restored from `sessionStorage` and re-validated with `/api/me` |

### Form (Create order, 3 steps: Customer → Items → Review)
| Case | Handling |
|---|---|
| Next clicked with invalid fields | Only the current step's fields are validated; errors shown inline |
| Same SKU added twice | Quantities are merged |
| Quantity above stock | Blocked inline with "Only N left" |
| Leaving with unsaved input | Browser confirm prompt |
| Server validation fails | Field errors from the server are mapped back onto the form |

### Performance
| Case | Handling |
|---|---|
| 10,000+ rows | Virtualized rows + cursor-paginated infinite query (pages of 200) |
| Rows re-rendering on every event | Rows are `memo`ised; only the changed order gets a new object |
| Large first load | Routes are lazy-loaded; error reporting SDK is loaded only if configured |

### Accessibility
- Table uses ARIA grid roles with `aria-rowcount` / `aria-rowindex` (needed because virtualized rows aren't all in the DOM).
- Drawer traps focus, closes on `Esc`, returns focus to the row.
- Status is never shown by colour alone (always has a text label).
- Toasts use `aria-live`.

## 6. Testing

| Layer | What is tested |
|---|---|
| Unit (Vitest) | State machine, permission rules, the function that applies live events to the cache, reconnect backoff maths |
| API (Vitest + real server) | RBAC on every write route, 409 on version conflict, idempotent create, stock checks |
| E2E (Playwright) | Login; manager vs viewer vs picker views; live update appears without refresh; status change; create-order happy path; blocked route |

## 7. Build phases

1. Monorepo + shared package (types, state machine, permissions) + tests
2. Server: seed data, auth, orders/inventory routes, RBAC
3. Server: WebSocket + simulator
4. Web: app shell, login, route guards
5. Web: orders table (virtualized, filters, infinite scroll)
6. Web: live updates (socket client, batching, cache patching, reconnect)
7. Web: order drawer (optimistic status change, assign, conflict handling)
8. Web: inventory page
9. Web: create-order multi-step form
10. Tests, README, deploy

## 8. Out of scope (on purpose)

- A real database (data resets on server restart)
- Real password security (demo accounts only)
- Mobile layout below 900 px (ops tools are used on desktops)

## 9. Deploy

- Web: Vercel or Netlify (static build of `apps/web`)
- Server: Render or Railway free tier (needs WebSocket support)
- Set `VITE_API_URL` on the web build to point at the server

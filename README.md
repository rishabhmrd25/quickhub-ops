# QuickHub Ops

A real-time operations dashboard for a quick-commerce **dark store** (a delivery-only mini warehouse).
Staff watch orders arrive live, assign pickers and riders, move orders through their stages, and manage stock.

> Learning project. All data is fake and generated by a local mock server. Not affiliated with any company.

## What it shows

- **10,000+ orders in a virtualized table** that stays smooth (only ~25 rows are ever in the DOM)
- **Live updates over WebSockets** with auto-reconnect, missed-event detection and batched rendering
- **Role-based access** (manager / picker / viewer), enforced on the server and reflected in the UI
- **Optimistic updates** with rollback, and conflict handling when two people edit the same order
- **Multi-step form** with per-step validation, stock checks and double-submit protection
- **Tests**: unit (Vitest), API (Vitest against a real server), end-to-end (Playwright)

## Stack

React 18 · TypeScript (strict) · Vite · TanStack Query · Zustand · TanStack Virtual · React Router ·
React Hook Form + Zod · Express + ws · Vitest · Playwright · npm workspaces monorepo

## Run it

```bash
npm install
npm run dev        # API on :4000, web on http://localhost:5173
```

## Key decisions

- **Server data in TanStack Query, browser-only data in Zustand.** Orders and stock are cached, retried and patched by Query. Zustand only holds the session, connection status and toasts.
- **Live events patch the cache instead of refetching.** One pure function (`applyOrderChanges`) decides what each event does to each cached list. It is the most-tested file in the project.
- **Cursor pagination, not page numbers.** New orders arrive at the top constantly; page numbers would shift and repeat rows.
- **Every order has a `version`.** It lets the server reject conflicting edits (409) and lets the client ignore out-of-date events.
- **The UI hides what a role cannot do; the server refuses it.** Both use the same rules from `packages/shared`.

## Environment variables

| Variable | Where | Default | Purpose |
|---|---|---|---|
| `PORT` | server | 4000 | API port |
| `SIMULATOR` | server | on | `off` stops the fake order flow |
| `LATENCY_MS` | server | 120 | Fake network delay, so loading states are visible |
| `TOKEN_SECRET` | server | dev value | Signs login tokens. Set this when deploying |
| `CORS_ORIGIN` | server | any | Comma-separated allowed origins |
| `VITE_API_URL` | web | (same origin) | API base URL when web and server are deployed separately |
| `VITE_SENTRY_DSN` | web | (off) | Turns on error reporting |

## Deploy

| Part | Host | Config |
|---|---|---|
| API + WebSocket server | Render (free web service) | [`render.yaml`](render.yaml) blueprint |
| Web app | Vercel | [`vercel.json`](vercel.json): installs at the repo root, builds `@quickhub/web`, rewrites every route to `index.html` so deep links like `/orders/ORD-1` survive a refresh |

Set `VITE_API_URL` on Vercel to the Render URL (the WebSocket URL is derived from it, `https` → `wss`),
and `CORS_ORIGIN` on Render to the Vercel URL.

> The free Render server sleeps after about 15 minutes without traffic, so the first load after a quiet spell can take 30–60 seconds. Data also resets when it wakes up.

## Known limits

- Data is in memory and resets when the server restarts.
- Auth is demo-grade (fixed accounts, simple signed token).
- Built for desktop widths; ops tools are used on store computers.
